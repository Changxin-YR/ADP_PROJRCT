# 企业业务调用流程

## 主数据与生产准备

完整调用顺序：登录 → 查询角色范围 → 建立基地/区域/塘组/塘口 → 提交 → 独立核验 → 建立养殖批次。主数据提交后仍可修改；每次修改递增版本并更新待办目标版本；核验后只读。

1. `POST /master-data/farms`、`areas`、`pond-groups`、`ponds` 创建草稿。
2. `POST /master-data/{resource}/{id}/submit` 进入待核验。
3. 另一账号调用 `POST /master-data/{resource}/{id}/verify`。
4. `POST /production/batches` 创建批次并按相同流程核验。
5. `GET /production/batches/{id}/reconciliation` 检查投苗、调拨、损耗和起捕数量差异。

## 日常养殖与仓储

完整调用顺序：饲料计划 → 任务 → 领料/出库 → 投喂记录 → 提交 → 核验 → 库存和批次事实入账。

生产记录资源包括批次、抽样、调拨、损耗、起捕、饲料计划、饲料任务、投喂记录和日常操作；仓储资源包括入库、领料、出库、退库、调拨、盘点和报废。资源名以 OpenAPI 路径参数说明及前端实际调用为准。

核验仓储单据会在同一事务内写库存流水、余额、待办和审计。`GET /warehouse/ledger` 是库存事实来源，`GET /warehouse/alerts` 是余额和效期的查询结果，不接受客户端直接写入。

## 采购、应付与付款

完整调用顺序：采购单草稿 → 提交 → 非经办人审批 → 仓储收货并核验 → 自动生成应付 → 付款草稿 → 提交 → 非经办人核验 → 应付余额更新。

采购审批本身不增加库存。只有收货核验才生成库存事实和唯一应付来源。部分收货、部分付款可重复发生，但每一张来源单只入账一次。付款核验需要凭证附件 ID，错误付款通过冲销记录修正，不能删除正式记录。

```json
{
  "expected_version": 2,
  "evidence_attachment_ids": [301]
}
```

## 销售、应收与收款

完整调用顺序：销售单草稿 → 提交 → 非经办人审批 → 交付关联已核验起捕单 → 交付核验 → 自动生成应收 → 收款草稿 → 提交 → 非经办人核验 → 应收余额更新。

销售审批不减少批次存量。交付核验才写批次事实并创建唯一应收来源。已核验交付如需改正，调用 `/deliveries/{id}/correct` 创建关联更正单。收款退回使用 `/receipts/{id}/reverse`，并保留原收款、冲销人、原因、凭证和审计链。

## 费用、资产与月结

完整调用顺序：费用/资产录入 → 提交 → 核验 → 确认入账 → 成本归集与分配 → 结算草稿 → 提交 → 核验 → 确认 → 净额报表。

1. 附件先通过 `POST /data-exchange/attachments` 上传，取得附件 ID。
2. 费用或资产核验请求带 `evidence_attachment_ids`。
3. `POST /cost/allocations` 执行成本分配，来源合计必须等于分配明细合计。
4. `POST /cost/settlements` 创建期间结算，再依次 submit、verify、confirm。
5. `GET /cost/reports/net` 查询已确认事实；期间锁定后禁止直接补写，必须更正或冲销。

## 附件、导入与导出

附件调用顺序：上传 → 绑定业务类型和记录 → 核验时引用附件 ID → 权限内下载。文件名由服务端生成，下载接口重新校验登录、能力码和数据范围。

导入调用顺序：下载带版本模板 → 上传预检 → 查看逐行错误 → 确认整批导入。任一行失败时整批回滚，并可下载错误工作簿；文件哈希用于防止重复确认。导出请求记录筛选范围、行数、操作者、生成时间和 `request_id`。

## 待办与审计

领域待办不能通过通用 `PATCH /work-items/{id}` 直接完成。它只负责导航到真实业务页面，完成核验后自动从待办队列移除并进入历史。通用接口仅处理 `workbench:manual` 手工待办。

审计查询只对超级管理员开放。审计表追加写入，记录请求 ID、操作人、动作、对象、前后状态和时间；任何 UI 或 API 都不提供删除审计记录的能力。
