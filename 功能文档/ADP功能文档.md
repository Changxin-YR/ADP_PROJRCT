## 一、文档说明

本文件只描述鱼塘养殖喂养日常管理系统“应该具备什么功能、用户如何使用这些功能、不同功能之间如何衔接”。本文件不规定程序采用什么技术、如何部署、数据库如何设计，也不规定页面必须采用哪一种代码实现方式。

本文件把完整目标功能作为产品基线。当前交付同时包含响应式 Web 管理端、Expo / React Native 移动 App 和微信小程序，三端统一连接 ADP 后端并复用同一套权限、业务规则与数据口径。核心版本覆盖电脑端管理、现场移动访问、塘口与批次管理、投喂闭环、仓储闭环、采购销售、成本核算、数据交换和权限审计；网络不稳定时保留现场已填写内容，避免作业记录丢失。

本文件是在以下内容基础上重新整理形成的全新功能文档：

1. 原鱼塘养殖管理网站的登录页、数据看板、塘口管理、日常喂养、物料管理、采购管理、销售管理、成本分析、数据交换、系统管理等页面和弹窗。
2. 《养殖业鱼塘喂养日常管理系统需求规格说明书》中的业务范围、角色职责、移动作业、库存、成本、报表和验收要求。
3. 《数据模版导入和导出》中的采购明细、应付账款、销售明细、应收账款、塘口扩展字段和九类养殖成本要求。
4. 基于原网站形成的优化版平台中已经出现并核验过的工作台、塘口档案、喂养记录、库存预警、系统管理、快速录入和统一预警等功能。

本文件中的“原网站功能”表示原网站已经展示或明确存在的能力；“优化版已核验”表示在当前优化版演示平台中已经看到并验证过的能力；“新增或扩展功能”表示在原网站基础上，为形成完整、可持续使用的管理系统而补充或细化的功能。

## 二、术语定义

以下术语在本文件中反复使用，为避免理解差异统一说明：

1. 饵料系数：鱼类每增重1千克所消耗的饲料千克数。它是养殖分析和存塘量估算的参考，不得替代现场盘点或抽样测量。系统应记录采用的系数、适用品种、适用阶段、有效期间和调整原因。
2. 存塘量：某个塘口某个养殖批次当前仍在塘内的养殖对象数量、重量或两者。系统应区分“估算重量”“估算数量”“现场实测重量”“现场抽样数量”和“人工修正值”，同时记录来源、时间、录入人、复核人和修正原因；不能把不同口径的数字混成一个无来源的当前值。
3. 九维成本：本系统将养殖成本细分为塘租、设备、基础建设、人工、电费、苗种、饲料、动保和其他费用九个维度，每个维度有各自的分摊依据。
4. 派工闭环：从喂养计划生成任务，经历派工、执行、核验、复盘的完整管理流程，每个环节都有责任人和时间记录。
5. 近效期优先分配：物料出库时，系统自动按照到期日从近到远排序，优先消耗即将到期的批次，减少过期浪费。
6. 事务回滚：批量导入数据时，如果文件中存在不合格行，系统将整批数据全部放弃写入（回滚），不会出现部分成功部分失败。
7. 生命周期流转：塘口从筹建到改造的状态变迁过程，每次状态切换记录时间、操作人和原因，形成完整的养殖时间线。
8. 数据范围：权限系统中控制用户可以查看和操作哪些塘口、分组或区域的数据，而不仅仅是控制功能入口。
9. 养殖批次：一次投苗或转塘形成的可独立追踪的养殖单元。批次应贯穿投苗、规格、投喂、死亡、转塘、抽样、出塘、销售和成本结算。
10. 损耗记录：死亡、逃逸、报损、抽样损耗或其他导致存塘量减少的事实记录，必须注明数量或重量、原因、时间、发现人和复核人。
11. 确认单据：已经完成必要审核、可以进入库存、应收应付或成本统计的业务单据。草稿、退回和作废单据不得重复计入正式统计。
12. 期间结算：对指定月份、养殖周期或批次锁定收入、成本、库存和应收应付的统计口径。结算后如需修改，必须通过更正或反结算留下痕迹。

## 三、功能导航结构

系统功能按业务工作组织为以下导航区域：

1. 登录与工作台：登录、个人工作区、消息提醒、今日待办、经营总览和统一预警。
2. 塘口与批次：塘口档案、多塘分组、投苗批次、规格抽样、损耗、转塘、出塘和生命周期。
3. 日常养殖：喂养计划、喂养记录、喂养派工闭环、巡塘、水质、换水、用药、增氧和设备维护。
4. 物料与仓储：物料档案、采购入库、其他入库、出库领用、仓间调拨、退库、盘点、报损报废、库存预警和仓储台账。
5. 采购与付款：供应商档案、采购单、到货管理、应付账款、付款、对账和采购报表。
6. 销售与收款：客户档案、出塘销售、销售单、应收账款、收款、退货或冲销、对账和销售报表。
7. 成本与经营：九类成本、费用登记、资产与租赁、成本分摊、期间结算、收益分析和经营报表。
8. 数据交换：模板下载、批量导入、校验预览、错误处理、撤销导入和数据导出。
9. 系统管理：用户账号、角色权限、数据范围、操作日志、消息规则和基础参数。

不同角色登录后，导航栏只显示其有权访问的菜单项。养殖作业员默认进入简化的工作台视图而非完整看板。

## 四、产品定位与总体目标

系统面向个体养殖户、中小型养殖基地和规模化水产养殖企业，帮助管理人员把塘口、投苗、投喂、巡塘、物料、采购、销售、成本和人员责任统一记录在同一个业务平台中。

系统的总体目标如下：

1. 让每一个塘口都有独立、连续、可追溯的电子档案。
2. 让每天的投喂、巡塘、换水、用药和增氧作业都有明确的任务、执行记录和责任人。
3. 让鱼料、渔药、消毒用品、设备耗材和养殖工具的采购、入库、领用、退库、盘点和预警形成完整闭环。
4. 让管理人员能够从全场、分组和单塘三个层级查看养殖状态、投喂情况、库存情况和成本情况。
5. 让采购付款、销售收款和养殖成本之间能够相互对应，帮助经营人员判断每个塘口、每个批次和整个基地的经营结果。
6. 让不同岗位只看到和处理自己职责范围内的内容，同时保留完整的操作记录，保证数据真实、责任清晰。
7. 让办公室管理和塘口现场作业保持连续，减少纸质台账、重复登记和事后补录。

## 五、用户角色与使用范围

### 5.1 超级管理员

超级管理员负责整个系统的基础管理和安全管理，可以查看全场业务数据，维护用户账号、岗位角色、数据范围和系统基础参数，处理权限调整、日志查询、数据导入导出和系统级通知。

超级管理员应能够：

1. 新增、编辑、停用、启用和删除用户账号。
2. 为用户分配岗位角色和负责的塘口、分组或区域。
3. 配置角色可以查看、新增、修改、删除、审核、出入库、导出和处理预警的范围。
4. 查看所有用户的登录和业务操作记录。
5. 维护养殖品种、物料分类、计量单位、养殖区域、投喂类型和预警规则等基础内容。
6. 查看全场看板、全量业务台账和导出报表。

### 5.2 养殖管理员

养殖管理员负责塘口经营和养殖过程管理，是喂养计划、日常作业、异常记录和养殖分析的主要管理人员。

养殖管理员应能够：

1. 建立和维护塘口档案及多塘分组。
2. 制定投喂计划和投喂标准。
3. 发布投喂任务，查看作业执行情况，审核养殖作业记录。
4. 处理异常投喂、巡塘异常、水质异常和病害相关记录。
5. 查看塘口、分组和全场的投喂、库存消耗、养殖进度和成本数据。
6. 审核或确认与养殖塘口相关的物料领用。
7. 导出养殖报表并进行养殖复盘。

### 5.3 养殖作业员

养殖作业员主要在塘口现场使用系统，负责执行当天的投喂、巡塘和其他养殖作业，并及时提交真实记录。

养殖作业员应能够：

1. 查看自己被分配的塘口和当天待办任务。
2. 查看当前塘口的投喂要求、历史记录和注意事项。
3. 快速录入投喂量、天气、鱼群摄食情况和现场异常。
4. 记录巡塘、换水、用药、增氧等非投喂作业。
5. 发起物料领用申请并查看申请状态。
6. 上传现场照片或其他作业凭证。
7. 查看自己的历史作业记录和待处理事项，但不能越权修改审核结果或系统配置。

### 5.4 仓储管理员

仓储管理员负责物料档案、采购到货、入库、出库、退库、盘点、库存预警和仓储台账。

仓储管理员应能够：

1. 建立和维护物料档案。
2. 登记采购入库和退货入库。
3. 按塘口、人员和用途办理物料出库或领用。
4. 办理剩余物料退库。
5. 发起并完成库存盘点，处理账面库存与实际库存的差异。
6. 处理低库存、临期和过期预警。
7. 查询、核对和导出完整的仓储流水和物料消耗台账。

### 5.5 采购人员

采购人员负责供应商维护、采购申请、采购订单、到货跟踪和采购对账准备，但不能单独确认付款或修改财务结算结果。

采购人员应能够：

1. 维护供应商档案、合作状态、账期和常用物料。
2. 登记采购申请和采购单据，填写物料、规格、数量、价格、到货日期和附件。
3. 跟踪待采购、采购中、部分到货、全部到货、已关闭和已取消状态。
4. 查看采购单与入库单、退货单和供应商对账明细的关联关系。
5. 提交付款申请，查看申请进度，但不能越权确认付款。
6. 导出采购明细、到货差异和供应商对账准备表。

### 5.6 财务人员

财务人员负责采购应付、销售应收、付款、收款、对账、结算和财务相关报表。财务人员可以查看业务来源，但不应擅自修改塘口、投喂或库存事实记录。

财务人员应能够：

1. 查看已确认采购、入库、销售和出塘单据形成的应付应收金额。
2. 登记一次或多次付款、收款、退款、冲销和坏账处理，并上传凭证。
3. 查看未付、未收、逾期、争议和已结清金额。
4. 与供应商、客户进行对账，记录差异、处理意见和确认人。
5. 按期间、供应商、客户、塘口、批次和单据状态导出财务报表。
6. 对已结算期间提出更正或反结算申请，不能直接无痕修改历史结果。

### 5.7 销售人员

销售人员负责客户档案、出塘安排、销售单据、发货或交付信息和客户对账准备。销售人员可以登记销售事实，但收款确认和坏账处理由财务人员完成。

销售人员应能够：

1. 维护客户档案、信用额度、账期和合作状态。
2. 根据可出塘数量和批次登记销售或出塘计划。
3. 关联客户、塘口、养殖批次、品种、规格、数量、单价和交付日期。
4. 查看销售单、出塘记录、退货或冲销记录及客户对账信息。
5. 导出销售明细、交付差异和客户对账准备表。

### 5.8 角色使用原则

1. 角色是岗位职责的集合，系统允许一个人兼任多个角色，但每个角色的授权动作和数据范围必须分别记录。
2. 采购、仓储、财务、销售和养殖审核尽量由不同人员承担；同一人员兼任时，涉及自己提交的高风险单据应由其他授权人员复核。
3. “系统审核人员”不是默认岗位，而是由管理员授予某类审核权限的人员。审核权限必须明确对应的业务范围、单据类型和数据范围。
4. 所有人都只能查看和处理其授权的数据范围；即使拥有某个菜单的访问权，也不能绕过数据范围查看其他区域或塘口。

## 七、登录、个人工作区与消息功能

### 7.1 登录功能

登录页面用于确认用户身份并进入对应的工作区。页面应提供手机号或账号、密码和登录按钮，并在用户输入不完整、账号不存在、密码错误或账号停用时给出清晰提示。

登录后，系统应根据用户角色和数据范围展示允许访问的功能。用户退出后，当前账号的工作区信息应被清除，下一位用户不能直接继承上一位用户的操作状态。

原网站展示了演示账号提示，优化版保留了演示环境的快速进入体验。正式使用时应把演示账号提示与生产账号分开，避免将真实账号或密码长期展示在登录页面。

登录安全规则：

1. 连续输入错误密码达到5次后，该账号临时锁定15分钟，锁定期间不接受登录请求。
2. 用户30分钟内无任何操作，系统自动退出当前会话，再次使用需重新登录。
3. 同一账号的同时登录数量应由管理员按岗位配置。高权限账号默认限制同时会话数量；发生新会话挤出旧会话时，旧会话应给出明确提示并记录安全日志，现场作业账号可以按需要允许多终端使用。
4. 密码长度不少于8位，必须同时包含字母和数字。
5. 密码不得直接使用账号、手机号、生日、连续数字或明显重复字符；系统应拒绝常见弱密码。
6. 超级管理员为用户创建账号时设置初始密码，用户首次登录后系统应强制要求修改密码方可进入工作区。

### 7.2 个人工作区

个人工作区用于展示当前用户最需要处理的内容，至少包括：

1. 当前用户姓名、岗位和负责范围。
2. 今日待办任务和逾期任务。
3. 待审核记录、库存预警或需要确认的单据。
4. 近期操作记录和个人完成情况。
5. 常用塘口或常用功能的快捷入口。

### 7.3 消息与提醒

系统应统一管理以下提醒：

1. 投喂任务即将到期或已经逾期。
2. 投喂记录待审核。
3. 投喂量偏离计划或存在异常天气、异常摄食情况。
4. 物料库存低于安全线。
5. 物料临近保质期或已经过期。
6. 采购应付款或销售应收款即将到期、已经逾期。
7. 盘点出现库存差异。
8. 数据导入完成、导入失败或存在待处理错误。
9. 系统管理员发布的通知。

每条提醒都应能打开对应的业务页面，并显示提醒来源、发生时间、关联塘口或物料、当前状态和处理入口。提醒处理后应保留处理人和处理时间。

提醒应区分未读、已读、处理中、已处理、已关闭和已升级状态。相同对象、相同原因在同一时间范围内重复触发时应合并显示，并保留发生次数；问题再次发生时应重新提醒。高严重程度提醒应能够指定接收人、升级时限和升级对象，用户关闭提醒时必须填写处理结论或说明。

消息中心是所有提醒的必达入口。用户在线时，应及时更新未读数量，并在不打断当前录入的前提下提示重要提醒；用户再次登录时，应能看到离线期间产生的未读消息。高优先级提醒可以按岗位配置浏览器通知、短信或其他外部触达方式，外部通知失败时不能影响站内消息留存，并应显示发送结果。

## 八、总览看板与经营驾驶舱

### 8.1 总览看板

总览看板是管理人员进入系统后的第一工作页面，用于快速判断全场养殖经营是否正常。原网站已经提供塘口总数、养殖状态、库存预警、预计利润、应收、应付和养殖成本等指标；优化版进一步将页面调整为围绕“今日养殖节奏、异常和库存”的工作台，并统一使用六种塘口正式状态。

看板至少应显示：

1. 塘口总数，以及筹建、放养、养殖、轮休、清塘、改造六种状态的数量。
2. 今日计划投喂量、今日实际投喂量、投喂完成率和待审核记录数。
3. 低库存、临期、过期和库存差异的数量。
4. 待执行、执行中、待核验、已核验和已复盘的派工数量；如需显示“已完成”，必须明确说明它是“已核验”和“已复盘”的合并展示，不得作为新的业务状态。
5. 本周期采购应付、销售应收、已付款、已收款和逾期金额。
6. 本周期养殖总成本、预计收入和预计利润。

### 8.2 看板筛选与周期切换

看板应支持按近七天、近三十天和全部时间查看数据，也应允许管理人员按自定义日期范围查看。原网站已有“近 7 天、近 30 天、全部”的统计周期选择，优化版应保留该习惯并补充当前筛选条件和数据更新时间。

看板可以按以下条件筛选：

1. 养殖区域、塘口分组和具体塘口。
2. 养殖品种、放养批次和负责人。
3. 投喂计划、饲料品类和作业人员。
4. 物料分类、供应商和库存状态。
5. 审核状态、异常状态和单据状态。

### 8.3 看板图表和下钻

看板应提供塘口状态分布、每日投喂趋势、各塘投喂量对比、物料可用库存、养殖成本构成和塘口收益对比等图表。

每个指标和图表都应支持继续查看明细。例如：

1. 点击“库存预警”可以查看具体物料、当前数量、安全线和处理记录。
2. 点击某个塘口可以打开该塘口的投喂、作业、物料和成本明细。
3. 点击某一天的投喂量可以查看当天每个塘口和每名作业员的记录。
4. 点击成本构成可以查看产生该成本的采购、入库、领用或费用单据。

### 8.4 看板导出

管理人员应能够导出当前周期、当前筛选范围内的看板数据。导出内容应包含统计时间、筛选条件、数据口径、汇总指标和明细入口，避免导出的数字脱离统计背景。

## 九、塘口管理功能

### 9.1 塘口档案

塘口档案用于建立“一塘一档”的基础资料和养殖生命周期记录。原网站已经提供塘号、品种、面积、放养数量、增氧机、状态、生命周期、负责人和分组等字段；补充资料又要求增加投苗规格、目前规格和当前存塘量估算。

新增或编辑塘口时，应能够填写：

1. 塘号，以及塘口的别名或内部编号。
2. 养殖区域、位置说明和可选的地图位置。
3. 面积、水深和其他基本环境信息。
4. 养殖品种、投苗批次、投苗数量、投苗日期和投苗单价。
5. 投苗规格、当前规格、规格更新时间和规格来源。
6. 当前存塘量，并明确该数据是人工录入、现场测量还是根据饵料系数估算。
7. 计划养殖周期、预计出塘日期和当前养殖阶段。
8. 增氧机数量、设备编号和设备状态。
9. 负责人、协作人员和所属分组。
10. 塘口照片、备案资料和其他附件。
11. 备注和风险提示。

### 9.2 塘口状态管理

塘口状态共六种：筹建、放养、养殖、轮休、清塘、改造。新建塘口只能从筹建或放养状态开始，不能直接设为养殖或其他状态。状态流转遵循有向规则，不可随意跳转，具体允许的流转路径如下：

1. 筹建可以流转至放养。
2. 放养可以流转至养殖（放养状态流转需双人核验确认）。
3. 养殖可以流转至轮休或清塘。
4. 轮休可以流转至放养或改造。
5. 清塘可以流转至轮休或改造（清塘状态流转需双人核验确认）。
6. 改造可以流转至筹建。

每次状态切换应记录切换时间、操作人员、原状态、目标状态、变更原因和核验人（需要双人核验的场景）。

状态流转路径可用以下文字图示理解：筹建 → 放养 → 养殖 → 轮休；养殖 → 清塘；轮休 → 放养或改造；清塘 → 轮休或改造；改造 → 筹建。除上述路径外，不得直接跳转；需要双人核验的流转必须完成核验后才能生效。

不同状态应影响后续操作：

1. 筹建和改造状态下，系统不允许录入日常投喂记录；但经授权的建设、维修、消毒和设备安装物料可以出库，并必须关联工程或维护事项。
2. 放养状态下，应允许录入投苗计划和投苗记录，但不计入正常养殖投喂统计。
3. 养殖状态下，系统应允许使用投喂、巡塘、物料消耗和成本功能。
4. 轮休和清塘状态下，系统应提醒用户确认后再录入日常养殖作业；清塘、检修、消毒等专门作业仍可按授权登记。
5. 状态变化应出现在塘口历史记录和管理看板中。

### 9.3 塘口查询、筛选与操作

塘口档案页面应支持按塘号、品种、负责人、区域、分组、养殖批次、状态和养殖时间检索。用户可以选择全部、筹建、放养、养殖、轮休、清塘和改造等状态快速筛选；状态筛选名称必须与塘口正式状态保持一致，不得再设置含义重复的临时别名。

每条塘口记录至少应提供以下操作：

1. 查看塘口详情和完整养殖时间线。
2. 编辑允许修改的基础信息。
3. 变更状态或转移负责人。
4. 查看该塘口的投喂、日常作业、物料消耗、成本和销售记录。
5. 导出单塘档案和单塘经营报表。
6. 停用或删除塘口。删除前必须判断该塘口是否已有业务记录；已有记录时应优先采用停用或归档，不能让历史台账失去关联。

### 9.4 多塘分组

多塘分组用于把多个塘口组成可批量管理的集合。系统应支持按区域、品种、放养批次、负责人或自定义规则建立分组。

分组功能应包括：

1. 新建、编辑、停用和删除分组。
2. 设置分组名称、分组说明、分组规则和所属塘口。
3. 查看分组内塘口数量、养殖状态、投喂进度、库存消耗和成本汇总。
4. 批量查看分组内塘口详情。
5. 为分组批量配置投喂计划或标准。
6. 导出分组养殖报表。
7. 在分组规则发生变化时保留变更记录。

### 9.5 投苗批次与养殖批次

系统应把投苗、转塘和出塘作为批次管理，而不是只在塘口档案中保存一个总数量。每个批次至少应记录：

1. 批次编号、来源单据和批次名称。
2. 养殖品种、苗种来源、供应商、规格、数量、重量、单价和投入金额。
3. 投苗日期、当前塘口、原塘口、负责人和批次状态。
4. 预计养殖周期、预计出塘日期、实际出塘日期和批次备注。
5. 批次当前存量、累计损耗、已转出数量或重量、已销售数量或重量。
6. 相关采购、入库、投喂、用药、抽样、转塘、出塘和销售单据。

系统应支持一个塘口同时养殖多个批次，也支持一个批次分到多个塘口。批次变更时应形成新的分支记录，不能覆盖原批次的历史数据。

### 9.6 规格抽样、损耗和转塘

养殖人员应能够定期登记抽样测量和存塘量校准，包括抽样日期、抽样塘口、批次、样本数量、平均规格、测量重量、推算存塘量、测量方法、天气水质、照片和复核人。系统应展示本次结果与上次结果的变化，并提示异常增减。

系统应支持登记死亡、逃逸、疾病损耗、抽样损耗、报损和其他损耗。损耗记录必须填写数量或重量、发生时间、原因、发现人、处理措施和复核结果，并自动影响批次存量、塘口存量和相关统计；已确认损耗不能直接删除，只能通过更正或冲销处理。

系统应支持塘口之间的转塘、分塘、合塘和批次拆分。转塘前应检查来源塘口存量，转塘后应同时更新来源和目标塘口，并保存转塘数量、规格、时间、经办人、核验人和原因。分塘、合塘不得破坏原批次与历史记录的关联。

### 9.7 起捕、出塘与批次结算

系统应提供从起捕计划到实际出塘的记录功能。出塘记录至少包括塘口、批次、品种、规格、数量或重量、起捕时间、损耗、去向、经办人、核验人和现场凭证。

出塘可以形成销售单，也可以登记为内部转移、留种、样品、赠送或其他非销售去向。出塘数量不得超过对应批次可出数量；部分出塘后，批次仍应保留剩余存量和后续操作入口。

批次关闭前，系统应提示未完成的投喂、用药、库存、损耗、销售和应收应付事项。批次关闭后，历史记录只允许查看和按权限更正，不允许通过普通编辑改变已结算结果。

### 9.8 生命周期与存量一致性

系统应同时展示塘口状态、批次状态和存量状态。塘口状态变化不能自动删除批次；清塘前应检查是否仍有存量，存在存量时必须先完成转塘、出塘或损耗确认。

当投苗、转塘、损耗、抽样校准和出塘造成存量变化时，系统应说明变化来源，并提供“账面推算值、最近实测值、人工修正值和最终采用值”的对照。不同模块引用的存量口径必须一致，发现差异时应生成待处理事项而不是静默覆盖。

## 十、日常喂养管理功能

### 10.1 喂养计划

喂养计划用于把养殖经验转化为可执行的每日标准。管理员应能够针对单个塘口或一个分组设定：

1. 适用的塘口、分组或养殖批次。
2. 养殖品种、养殖阶段和适用季节。
3. 每日投喂次数和每次投喂时间。
4. 标准投喂量、计量单位和允许偏差范围。
5. 使用的饲料品种和投喂规格。
6. 生效日期、结束日期和计划版本。
7. 雨天、低温、高温、低溶氧、少食等特殊条件下的调整说明。

创建计划后，系统应展示计划的适用对象、类型、每日次数、标准投喂量和投喂时间段。修改计划时，应允许选择“只影响未来任务”或“同时修正尚未执行的任务”，避免改变已经完成的历史记录。

### 10.2 喂养派工闭环

喂养派工用于把计划转为具体工作任务，形成“计划—派工—执行—核验—复盘”的闭环。

派工应包括：

1. 从喂养计划生成任务，或手动新建临时投喂任务。
2. 指定塘口、计划投喂量、投喂时间和作业人员。
3. 设置任务期限、优先级和注意事项。
4. 记录作业员接单、开始执行、完成提交和异常说明。
5. 由养殖管理员核验实际投喂量、执行时间和现场情况。
6. 自动计算计划量与实际量的偏差。
7. 对偏差超出范围、逾期执行或未完成任务发出提醒。
8. 在核验完成后生成可用于统计和复盘的正式记录。

任务状态包括待执行、执行中、待核验、已核验、已复盘和已取消。各状态必须有明确的进入条件、责任岗位和可执行动作：

1. 待执行：新建或从计划生成后的初始状态，可流转至执行中或已取消。
2. 执行中：作业员录入实际投喂量后进入此状态，可流转至待核验。
3. 待核验：作业员提交完成后等待管理员核验，可流转至已核验或退回至执行中。
4. 已核验：管理员确认偏差和记录无误后进入此状态，可流转至已复盘。
5. 已复盘：管理员填写复盘结论、偏差原因、改进措施和后续跟进人后闭环完成，为终态。
6. 已取消：任何尚未完成的任务均可取消，取消时必须填写原因、取消人和是否需要补派任务。
7. 只有作业员可以提交执行结果，只有被授权的养殖管理员或系统审核人员可以核验，只有复盘责任人可以关闭复盘；提交人不能核验自己的异常记录。
8. 计划变更只影响尚未执行的任务；已经核验或复盘的历史任务不能因计划修改而被重新计算。

### 10.3 投喂记录

投喂记录是每一次实际投喂的事实记录。原网站已经提供录入投喂、按塘口和状态筛选、只看异常、导出和审核入口；优化版增加了快速录入、计划与实际对照以及统一异常提醒。

投喂记录应包含：

1. 投喂日期和具体时间。
2. 塘口、所属分组和养殖批次。
3. 饲料名称、规格、批次和投喂数量。
4. 计划投喂量、实际投喂量和差异数量。
5. 作业人员和现场负责人。
6. 天气、水温、水质、溶氧或其他现场环境情况。
7. 鱼群摄食状态，如正常、少食、拒食或异常抢食。
8. 异常原因、处理措施和跟进结果。
9. 现场照片或其他凭证。
10. 当前状态，如待审核、已审核、已作废或异常待处理。

### 10.4 喂养记录审核

养殖管理员应能够按日期、塘口、分组、作业员、审核状态和异常状态筛选记录，并进行逐条或批量审核。

审核时应能够查看计划量与实际量、现场情况、照片、异常说明和关联物料消耗。审核结果可以是通过、退回修改、标记异常或作废。退回和作废必须填写原因，原始记录不能被无痕覆盖。

### 10.5 喂养统计

系统应按日、周、月、年度、单塘、分组和全场统计：

1. 投喂总量和单次平均投喂量。
2. 计划完成率和准时执行率。
3. 各塘口投喂量对比。
4. 各饲料品类消耗趋势。
5. 异常投喂数量和异常原因分布。
6. 计划量与实际量的偏差趋势。
7. 与投苗量、当前规格、存塘量估算相关的投喂表现。

## 十一、日常作业与养殖巡检功能

日常作业用于记录除投喂之外的现场工作。原网站已经展示巡塘、换水、用药和增氧等非投喂作业类型，优化版应将其作为与投喂记录并列的养殖作业台账。

### 11.1 作业记录

作业员或管理员应能够新建以下类型的作业：

1. 巡塘：记录水面、鱼群活动、死鱼、病害、水质和环境观察结果。
2. 换水：记录换水数量、水源、开始时间、结束时间和结果。
3. 用药或消毒：记录药品名称、用量、使用方式、关联塘口和安全间隔要求。
4. 增氧：记录设备、运行时长、开启原因、设备状态和处理结果。
5. 水质检测：记录检测项目、检测值、检测时间和是否超出标准。
6. 设备维护：记录设备、故障、维修内容、维修人和完成时间。
7. 其他养殖作业：允许管理员配置类型并填写作业说明。

### 11.2 作业查询与关联

作业记录应支持按塘口、作业类型、人员和时间筛选，展示作业参数、结果、操作人员和时间。涉及药品、消毒用品或其他库存物料时，应能够关联出库记录；涉及异常时，应能够关联预警、待办和后续处理结果。

## 十二、物料档案与仓储管理功能

### 12.1 物料档案

物料档案用于统一管理鱼料、渔药、消毒用品、增氧耗材、设备配件和养殖工具。

物料档案应包含：

1. 物料名称、物料编号和物料分类。
2. 规格型号、包装规格和计量单位。
3. 采购单价或最近采购价格。
4. 供应商和默认供应商信息。
5. 保质期、存放位置和储存要求。
6. 安全库存、最低库存和临期预警天数。
7. 是否可以用于投喂、用药、消毒、增氧或其他作业。
8. 备注、图片和相关凭证。

物料页面应支持新建、编辑、停用、查询、筛选、导出和查看库存流水。已经产生业务记录的物料不能直接删除，应采用停用方式保留历史关联。

### 12.2 物料入库

入库用于登记采购到货或其他来源的物料进入仓库。入库时应能够选择物料、数量、单位、入库类型、批次、生产日期、到期日期、供应商和存放位置，并上传采购合同、送货单或验收凭证。

系统应区分采购入库和退货入库，并为每一次入库生成唯一单号。入库完成后，应能够看到库存增加、批次变化和对应单据。入库记录一旦确认，修改或撤销必须经过权限控制并保留原因。

### 12.3 物料出库与领用

出库用于把物料从仓库发给作业人员、某个塘口或其他用途。出库时应填写：

1. 物料和可用库存。
2. 出库数量和计量单位。
3. 出库场景，如日常投喂、用药、消毒、设备维修或其他用途。
4. 关联塘口、分组或作业任务。
5. 领用人、审批人和领用时间。
6. 备注或凭证。

出库前应提醒可用库存，禁止形成负库存。出库完成后应自动减少库存，并把消耗归集到关联塘口、作业任务和成本核算中。

出库场景与塘口关联规则：

| 出库场景 | 是否必须关联塘口 | 说明 |
|---------|----------------|------|
| 日常投喂（喂养） | 必填 | 饲料消耗必须归集到具体塘口 |
| 用药 | 必填 | 药品使用必须追溯到塘口，用于安全间隔管控 |
| 换水 | 条件必填 | 只有发生物料消耗时必须关联塘口；纯作业记录可只登记作业地点 |
| 设备维修 | 选填 | 可关联具体塘口设备或不关联（公共设备） |
| 调拨 | 不填 | 仓库间调拨不涉及塘口消耗 |
| 报损 | 不填 | 过期、损坏报废不归入塘口成本 |

出库时系统应执行近效期优先分配：自动按批次到期日从近到远排序，优先消耗即将到期的批次，并在出库单中显示各批次实际扣减明细。用户确需指定其他批次时，可以手动覆盖自动分配，但必须选择或填写覆盖原因，并由有权限的人员确认。

### 12.4 物料退库

退库用于处理未使用、剩余或需要退回仓库的物料。退库时应选择原物料和批次，填写退库数量、退库原因、退库人、验收人和退库时间。

退库完成后，库存应恢复相应数量，并保留原出库与本次退库之间的关联。已开封、损坏或无法再次使用的物料，应允许标记为不可用并说明处理方式。

### 12.5 库存盘点

库存盘点用于核对账面数量与实际数量。系统应支持临时盘点、月度盘点和年度盘点。

盘点时应展示物料、批次、账面库存、实际库存、差异数量、差异原因、盘点人和复核人。盘点完成后应生成盘点差异记录；差异调整必须由有权限的人员确认，并且不能删除原始账面流水。

### 12.6 库存预警

系统应根据物料的安全库存、保质期和当前时间生成以下预警：

1. 库存不足：可用库存低于安全线。
2. 临近到期：距离到期日小于预设天数。
3. 已过期：已经超过到期日。
4. 盘点差异：实际库存与账面库存不一致。
5. 长期未使用：物料长期占用库存但没有消耗记录。

预警中心应显示物料、预警类型、严重程度、当前数值、发生时间和处理状态。用户可以点击“处理”进入补货、调拨、报废、复核或修改预警阈值的业务动作。

### 12.7 仓储台账

仓储台账应能按照物料、批次、供应商、塘口、作业员、单据类型和时间查询所有库存变化。每一笔流水都应能回到入库单、出库单、退库单、盘点单或关联作业，形成完整的物料追溯链。

### 12.8 仓间调拨

系统应支持同一基地不同仓库、库位或保管责任人之间的调拨。调拨单应记录调出仓、调入仓、物料、批次、数量、调拨原因、申请人、发出人、接收人和确认时间。

调拨应经过“申请—发出—接收—完成”或“取消”流程。调出后未接收的数量应显示为在途库存，不能同时计入两个仓库的可用库存；接收数量与发出数量不一致时必须登记差异和处理结果。

### 12.9 报损、报废与过期处理

仓储人员应能够登记物料报损、报废、过期隔离和销毁。记录应包含物料、批次、数量、原因、照片或凭证、申请人、复核人和处理日期。

报损报废必须先从可用库存中隔离，经过授权确认后才减少账面库存；过期物料不得被普通出库选择。报损报废不计入塘口消耗，但应进入库存损耗和经营分析。

### 12.10 库存申请与领用闭环

作业员或养殖管理员可以按任务、塘口、批次或维修事项发起领用申请。申请应包含用途、物料、数量、期望领取时间和关联业务。

仓储人员应能够审核申请、调整实际发放数量、选择批次、办理出库并记录领用人。申请被退回、部分满足或取消时，应显示原因；出库后实际消耗与退库数量应能回到原领用申请，形成“申请—出库—使用—退库”的闭环。

## 十三、采购与应付账款功能

### 13.1 采购明细

采购管理用于记录鱼料、鱼苗、虾苗、渔药、设备和其他养殖物资的采购业务。登记采购时应填写供应商、物料、规格、数量、单价、计量单位、金额、到期日、备注和相关凭证。

采购记录应包含单号、供应商、物料、规格、数量、单价、总金额、已付款、未付款、到期日、当前状态和关联入库单。采购到货后可以直接进入入库登记，减少重复录入。

### 13.2 采购状态与到货管理

采购单应至少支持草稿、待审核、已确认、采购中、部分到货、全部到货、部分退货、已关闭、已取消和争议处理等状态。状态应由业务事实推动，不能仅由人员手工改成任意值。

采购人员应能够登记预计到货、实际到货、短缺、破损、批次、生产日期和到期日期。部分到货时，系统应保留未到货数量；全部到货且差异处理完成后才能关闭采购单。取消或关闭采购单前，应检查是否已经入库、付款或产生应付账款。

采购单的修改、取消、退货和价格调整都必须注明原因并保留前后内容。已经形成入库或付款的单据不能直接删除，只能通过退货、红字更正或冲销处理。

### 13.3 应付账款

应付账款页面应展示应付总额、已付金额、未付金额和逾期单数。用户可以按照供应商、采购单号、付款状态和到期日筛选。

每一笔应付款应支持：

1. 查看采购明细和对应入库记录。
2. 登记一次或多次付款。
3. 查看付款时间、金额、付款方式、经办人和凭证。
4. 查看剩余应付金额和逾期天数。
5. 对账并导出供应商对账单。
6. 标记争议、暂缓付款或已结清，并说明原因。

付款应支持分次付款，但累计付款不得超过确认后的应付金额；发生退款、折让或冲销时，应关联原付款并保留凭证。付款录入后应进入待复核或已确认状态，未确认的付款不能改变正式应付余额。

### 13.4 采购提醒与报表

系统应对即将到期和已经逾期的应付款提醒相关人员，并支持按供应商、月份、物料类别和塘口关联情况导出采购与付款报表。

## 十四、销售与应收账款功能

### 14.1 销售明细

销售管理用于记录鱼、虾或其他养殖产品的销售。登记销售时应填写客户、销售单号、关联塘口、养殖品种、数量、单位、单价、金额、销售日期、到期日、备注和凭证。

销售页面应展示客户、塘口、品种、数量、单价、总金额、已收、未收、到期日、状态和操作入口。销售数据应能与塘口的出塘、养殖批次和预计收入关联。

### 14.2 出塘与销售状态

销售应区分“出塘事实”和“销售交易”。出塘事实用于减少批次存量，销售交易用于确认客户、价格和应收账款；内部转移、留种、赠送和损耗不得被误计为销售收入。

销售单应至少支持草稿、待审核、已确认、待交付、部分交付、已交付、部分收款、已结清、已取消、退货或冲销、争议和坏账处理等状态。只有已确认的销售单才进入收入和应收统计。

销售人员应能够登记交付数量、交付时间、运输或提货信息、客户验收和差异；发生部分交付时应保留未交付数量。退货、少交、多交、价格调整和销售冲销必须关联原单据并记录原因。

### 14.3 应收账款

应收账款页面应展示应收总额、已收金额、未收金额和逾期单数。用户可以按照客户、塘口、销售单号、收款状态和到期日筛选。

每一笔应收款应支持：

1. 登记一次或多次收款。
2. 查看收款时间、金额、方式、经办人和凭证。
3. 查看剩余未收金额和逾期天数。
4. 对账并导出客户对账单。
5. 标记已结清、部分收款、争议或坏账处理状态，并记录原因。

收款应支持分次收款，但累计收款不得超过确认后的应收金额；多收、退款、折让和坏账核销必须通过独立的更正或冲销记录处理。未确认的收款不能改变正式应收余额。

### 14.4 销售分析

系统应按客户、品种、塘口、月份和销售批次统计销售数量、销售金额、收款进度和平均销售价格，并为养殖成本和利润分析提供收入数据。

### 14.5 供应商与客户档案

系统应独立管理供应商和客户的基础信息，供采购和销售模块引用。

供应商档案应包含：

1. 供应商名称、联系人、联系电话和地址。
2. 主营物料类型和常用物料清单。
3. 合作状态（合作中、暂停合作、已终止）。
4. 对账周期（月结、到货付款或自定义账期）。
5. 累计采购金额、累计付款金额和当前应付余额。
6. 关联的采购单据和入库记录。
7. 备注和评价。

客户档案应包含：

1. 客户名称、联系人、联系电话和地址。
2. 常购品种和历史采购偏好。
3. 合作状态（活跃、沉寂、已终止）。
4. 对账周期和信用额度。
5. 累计销售金额、累计收款金额和当前应收余额。
6. 关联的销售单据和收款记录。
7. 备注和评价。

供应商和客户有历史业务记录时不可直接删除，应使用停用方式保留关联完整性。

## 十五、养殖成本核算与经营分析功能

### 15.1 成本总览

成本分析页面应展示全场总成本、参与核算的塘口数量、成本分摊提示、预计收入和预计利润。所有成本数字都应能查看统计周期、分摊规则和来源明细。

### 15.2 九类成本

系统应至少核算以下九类养殖成本：

1. 塘租：按照年度租金，按月、按年度并按照面积分摊到每个塘口。
2. 设备：按照塘口对应的设备数量或设备价值计入，重点包括增氧机及其他专用设备。
3. 基础建设：按照基础建设投入和预计使用年限，并结合面积分摊。
4. 人工：按照每月人工费用，并结合塘口面积或实际工作范围分摊。
5. 电费：按照设备数量、运行时长或实际电费记录分摊。
6. 鱼苗或虾苗：按照实际投苗数量和实际投入金额计入。
7. 饲料：按照实际采购、入库和领用消耗计入。
8. 动保：按照实际使用的渔药、消毒用品和其他养殖保护用品计入。
9. 其他费用：允许录入运输、维修、检测、保险和其他未归入前八类的费用。

### 15.3 成本分摊

系统应能够按照塘口、分组、养殖批次和时间周期查看成本。分摊时应明确使用的依据，例如面积、设备数量、实际投入、实际消耗、运行时长或人工指定比例。

每个塘口应能看到塘租、设备、基础建设、人工、电费、苗种、饲料、动保和其他费用的分项金额、合计金额、单位面积成本和单位产量成本。

成本分摊边界规则：

1. 按面积分摊时，若所有参与核算塘口面积均为0，则改为均摊（平均分配到各塘口）。
2. 按设备数分摊时，若所有参与核算塘口设备数均为0，则改为均摊。
3. 按运行时长、实际工作范围或其他数量依据分摊时，若所有参与核算塘口的依据值均为0，则统一改为按参与塘口数量均摊，并在核算结果中标注“因分摊依据缺失已改为均摊”。
4. 新增塘口参与当期分摊从建档日期开始计算，不追溯调整之前已核算的历史成本。
5. 停用塘口退出分摊从停用日期开始，停用前已产生的成本记录保持不变。
6. 每次核算结果都应记录核算时间、核算人、分摊规则版本和参与塘口清单，确保不同时间导出的成本报表可解释差异。

### 15.4 成本图表与核算结果

系统应提供九维成本构成图、各塘口成本对比图、成本趋势图、收入与成本对比图和预计利润图。用户可以从图表进入对应的费用、采购、领用、销售或人工记录。

核算结果应允许重新计算，但每次核算都要记录核算时间、核算人、核算周期、分摊规则和结果版本，避免不同时间导出的成本报表无法解释。

### 15.5 成本来源登记

系统应提供与九类成本对应的费用和资产登记入口，不能只在报表中显示一个无法追溯的数字。至少包括：

1. 塘租合同：出租方、租赁范围、起止日期、租金、付款周期、面积、押金、凭证和合同状态。
2. 设备资产：设备名称、编号、类别、购买日期、原值、使用年限、当前状态、所属塘口或公共资产、维护记录和报废记录。
3. 基础建设：建设项目、位置、开始和完成日期、投入金额、预计使用年限、供应商、验收资料和分摊范围。
4. 人工费用：人员、工种、工作日期或期间、工作量、费用金额、负责塘口或分组、审批人和凭证。
5. 电费及公共费用：计费期间、表计或费用来源、金额、关联设备或区域、分摊依据和凭证。
6. 苗种投入：投苗批次、苗种数量或重量、单价、金额、供应商、入库或投苗单据。
7. 饲料和动保消耗：从确认的入库、出库、退库和领用记录取得实际消耗，并允许补充外部消耗凭证。
8. 其他费用：费用类别、金额、发生日期、付款情况、关联塘口或分组、分摊依据和附件。

每笔费用都应有草稿、待审核、已确认、已冲销或已作废等状态。只有已确认的费用进入正式成本核算；冲销或更正必须关联原费用并保留原金额。

### 15.6 核算周期、结算与更正

系统应支持按日、月、养殖周期和批次进行核算，并允许设置月度截止时间。管理人员应能够查看本期新增数据、待审核数据、未分摊数据和可能影响结果的异常。

期间结算时，应锁定本期收入、成本、库存消耗、损耗和存量口径，并生成结算摘要。结算后如需补录或更正，应显示对原结果的影响，经过授权后重新结算；禁止直接覆盖已发布的历史报表。

重新核算时，系统应提供旧版本与新版本的差异，包括受影响塘口、批次、成本类别、收入、利润和变更原因。每个版本都应能够重新打开查看。

### 15.7 收益与批次经营分析

系统应支持按塘口、养殖批次、品种、分组和期间分析投入、产出、收入、成本、损耗和预计利润。分析结果应区分“已确认事实”和“预测值”，并明确预测所依据的存量、单价、饵料系数和未结算费用。

管理人员应能够查看单个批次从投苗到出塘的投入产出明细，比较不同塘口的单位面积成本、单位产量成本、饵料系数、成活率、销售价格和利润贡献。

### 15.8 资产、租赁与维护关联

设备和基础建设资料应能够关联塘口、分组或公共区域，并支持维护、停用、转移、报废和责任人变更。设备维修产生的物料、人工和其他费用应能回到设备维护事项，再按规则进入对应成本，不得只形成孤立的库存或费用记录。

## 十六、数据导入、导出与模板管理功能

### 16.1 模板下载

数据交换页面应让用户先选择数据类型，再下载对应标准模板。模板应清楚说明每一列的含义、是否必填、允许的格式、计量单位和示例。

至少应提供塘口档案、养殖批次、投苗记录、规格抽样、损耗记录、转塘记录、喂养计划、喂养记录、派工任务、日常作业、物料档案、入库记录、出库记录、调拨记录、退库记录、盘点记录、报损报废记录、供应商、采购明细、付款记录、客户、销售明细、出塘记录、收款记录、费用登记、设备资产、租赁合同、成本调整和基础参数等模板。

核心模板字段规范如下：

塘口档案模板：塘号（必填）、面积（必填，数字）、水深（数字）、品种（必填）、放养数（数字）、状态（限定值：筹建/放养/养殖/轮休/清塘/改造）、负责人、增氧机数量（数字）、投苗规格、目前规格。

物料档案模板：名称（必填）、分类（必填）、规格、单位、单价（数字）、供应商。

采购明细模板：供应商（必填）、物料（必填）、规格、数量（必填，正数）、单价（必填，正数）、金额（数字）、到期日（日期格式YYYY-MM-DD）、备注。

销售明细模板：客户（必填）、塘口、品种、数量（必填，正数）、单价（必填，正数）、金额（数字）、销售日期（日期格式）、到期日（日期格式）、备注。

养殖批次模板：批次编号（必填且唯一）、品种（必填）、来源、规格、投苗日期、投苗数量或重量、单价、金额、当前塘口（必填）、预计出塘日期、负责人、批次状态。

投喂记录模板：日期时间（必填）、塘口（必填）、批次、饲料（必填）、批次号、计划量、实际量（必填且为正数）、作业员、天气、摄食状态、异常说明、审核状态。

损耗与转塘模板：业务类型（损耗/转塘/分塘/合塘）、原塘口或原批次、目标塘口或目标批次、数量或重量、发生时间、原因、经办人、核验人和凭证。

库存流水模板：物料、批次、业务类型、数量、单位、来源或去向仓库、关联塘口或任务、经办人、发生时间和单据号。

费用与资产模板：费用类别或资产类别、发生日期、金额、供应商或人员、关联塘口/分组/公共区域、分摊依据、凭证和审核状态。

### 16.2 批量导入

用户选择文件后，系统应先展示文件名称、数据行数、识别出的列和待导入内容，再由用户确认导入。导入前应检查：

1. 文件格式是否正确。
2. 模板列是否完整。
3. 必填字段是否为空。
4. 日期、数量、金额和状态是否符合要求。
5. 塘口、物料、供应商、客户等关联对象是否存在。
6. 是否存在重复单号、重复塘号或重复物料编号。
7. 是否存在超出业务范围的负数、错误单位或非法状态。

### 16.3 校验结果与事务回滚

导入结束前应显示总行数、通过行数、错误行数和错误原因。用户可以下载错误明细并修正原文件。

当文件中存在不合格数据时，系统应默认整批不写入，不能出现一部分成功、一部分失败而用户不知情的情况。用户确认重新导入后，系统应再次从头校验。

### 16.4 数据导出

用户应能够从各业务页面导出当前筛选范围内的数据，也可以导出全场汇总或指定塘口、分组、物料、供应商和时间范围的数据。导出文件应包含生成时间、导出人、筛选条件和数据口径。

### 16.5 导入批次、重复和撤销

每次导入都应形成导入批次，记录导入人、导入时间、文件名称、模板版本、数据类型、行数、校验结果和处理结果。用户应能够查看导入批次详情，并在尚未被后续业务引用时撤销整批导入。

重复数据应按数据类型分别处理：塘号、物料编码、批次编号和单据号原则上必须唯一；同一业务单据重复导入时应明确提示“跳过、覆盖、生成新单或取消”，不能默默产生重复库存、重复应收或重复成本。已经进入后续业务的记录不得通过重新导入直接覆盖。

导入校验除格式和必填项外，还应检查塘口状态、批次存量、库存可用量、单据状态、日期先后关系、金额与数量单价关系以及跨表关联。错误结果应定位到行和列，并给出可执行的修正建议。

### 16.6 报表与导出范围

导出应支持明细表、汇总表、统计图表和凭证清单。用户应能够选择当前结果、指定条件、指定期间、单塘、分组、批次或全场范围，并在导出前查看数据条数和统计口径。导出的内容应按用户权限过滤，不能因导出而扩大数据范围。

## 十七、系统管理功能

### 17.1 用户账号管理

用户账号页面应展示姓名、手机号或账号、岗位角色、负责塘口、账号状态和操作入口。管理员应能够新增、编辑、停用、启用、重置登录凭证和删除账号。

新增用户时应填写姓名、手机号、初始登录凭证、角色、负责塘口或数据范围以及账号状态。停用用户后，该用户不能继续登录，但历史操作记录和已提交业务记录必须保留。

### 17.2 角色权限管理

权限应同时考虑“能访问什么功能”和“能访问哪些数据”。系统应支持为角色配置查看、新增、修改、删除、审核、出入库、处理预警和导出等动作，并设置全场、区域、分组、塘口或个人数据范围。

角色权限页面应能够：

1. 查看每个角色的功能权限。
2. 修改角色权限并显示变更前后差异。
3. 复制已有角色作为新角色的起点。
4. 设置角色是否允许处理敏感数据、财务数据或权限数据。
5. 查看角色下当前用户数量。
6. 对高风险权限变更要求再次确认。

### 17.3 操作日志

系统操作日志应记录登录、退出、新增、修改、删除、审核、出入库、盘点、导入、导出、权限变更、状态变更和预警处理等行为。

日志应至少显示时间、用户、操作类型、业务对象、对象编号、操作结果和详细说明，并支持按用户、操作、时间范围、模块和结果筛选。日志应可以导出，但导出的日志不应泄露密码、密钥或其他敏感凭证。

### 17.4 基础参数

基础参数页面应支持维护：

1. 养殖品种。
2. 物料分类。
3. 计量单位。
4. 养殖区域。
5. 饲料类型。
6. 喂养异常类型。
7. 日常作业类型。
8. 库存安全线和临期预警天数。
9. 养殖状态和单据状态。
10. 成本分类和分摊规则名称。

基础参数修改后，应提示会影响哪些后续业务，不应改变已经完成业务记录的历史含义。

## 十八、多终端访问与现场作业功能

当前交付覆盖响应式网页、独立移动 App 和微信小程序。电脑浏览器适合看板、台账、批量审核和报表；手机浏览器、移动 App 与小程序适合接收任务、快速录入、拍照取证、塘口查询和查看个人待办。移动 App 与小程序均复用 Web 端后端 API，不建立独立业务台账。

系统应同时满足办公室管理和塘口现场作业。电脑浏览器和手机浏览器使用同一套业务规则和权限范围，不能因为入口不同而产生两套互相矛盾的数据。

现场访问应提供简化的作业工作区：

1. 导航栏折叠为底部标签栏或汉堡菜单，优先展示今日任务、常用塘口、快速投喂和物料领用入口。
2. 表单在移动视图下减少非必填字段的默认展示，增大输入框和按钮的触摸区域。
3. 列表页在移动视图下采用卡片式布局替代宽表格，关键信息前置。
4. 选择或收藏常用塘口，减少现场搜索操作。
5. 快速填写投喂量、天气、摄食状态和异常原因。
6. 支持通过手机浏览器调用相机拍照上传现场情况。
7. 查看个人当天和历史作业记录。
8. 在提交前提示必填项、数量范围、存量限制和关联塘口。
9. 接收任务到期、审核退回、异常升级和库存领用结果的通知。
10. 在网络不稳定时暂存未提交内容，恢复连接后允许用户确认并继续提交，提交成功前不得标记为正式记录。
11. 对同一条现场记录显示同步状态，避免用户误以为暂存内容已经进入正式台账。
12. 支持扫码或拍照识别物料、设备、塘口或单据，但识别结果必须由用户确认后才能写入业务记录。

三端应共同验收登录与会话、任务查看、投喂录入、非投喂作业、塘口与批次、照片上传、弱网暂存、同步冲突处理和消息接收能力。移动 App 还覆盖仓储、采购、销售、成本与数据交换入口；小程序聚焦现场投喂、日常作业、物料领退、塘口、消息和个人中心。

## 十九、跨模块业务闭环

### 19.1 日常喂养闭环

养殖管理员制定投喂计划，系统根据计划生成任务；作业员收到任务后到现场执行投喂，填写实际数量和现场情况并上传照片；管理员审核或退回记录；系统根据审核结果汇总投喂量、饲料消耗、异常情况和成本；管理人员在看板中查看趋势并导出复盘报表。

### 19.2 物料闭环

采购人员登记采购，仓储人员验收并办理入库；作业员按任务或塘口申请领用，仓储人员审核并出库；作业完成后，未使用物料可以退库；仓储人员定期盘点，系统根据库存变化生成低库存、临期、过期和差异预警；物料消耗自动归集到塘口和成本。

### 19.3 多塘管控闭环

管理员建立塘口档案并按区域、品种、批次或负责人分组；各塘口独立产生投喂、巡检、库存消耗和成本记录；系统同时提供单塘、分组和全场视图；管理员通过筛选、看板和报表进行横向比较和养殖复盘。

### 19.4 采购付款闭环

采购人员登记采购单，仓储人员根据到货情况形成入库记录，财务人员根据采购单和供应商对账登记付款，系统自动计算应付、已付、未付和逾期金额，并允许导出对账结果。

### 19.5 销售收款闭环

销售人员登记销售单并关联出塘塘口和品种，财务人员登记客户收款，系统自动计算应收、已收、未收和逾期金额，并把销售收入提供给成本和利润分析。

## 二十、通用业务规则

1. 所有新增、修改、删除、审核、出入库、盘点、导入和导出行为都应记录操作人和时间。
2. 有历史业务关联的塘口、物料、用户和基础参数原则上不直接删除，应采用停用、归档或版本变更。
3. 库存数量不能因为出库或领用形成负数；库存不足时应先提示并阻止提交。
4. 计划量、实际量和差异量必须同时可见，不能只保存一个最终数字。
5. 财务金额应能追溯到采购、销售、付款、收款、入库或领用单据。
6. 任何异常记录都应能说明异常原因、处理措施、处理人和处理结果。
7. 导入文件出现错误时，系统应提供完整错误反馈，不得静默忽略错误行。
8. 导出数据应包含筛选条件和生成时间，确保后续审核时能够解释报表口径。
9. 用户只能访问被授予的功能和数据范围，不能通过搜索、导出或链接绕过权限限制。
10. 关键操作应有明确的成功、失败、待审核、退回、取消和处理中状态，不能只用无含义的颜色或图标表示。
11. 任何会改变存量、库存、应收应付、成本或收入的业务，都必须有来源单据、确认人和时间；草稿、退回和作废单据不能进入正式统计。
12. 同一事实不得在多个模块重复记账。投苗、转塘、损耗、出塘、入库、领用、付款和收款等业务应以一个正式单据为主记录，其他页面只引用或展示。
13. 状态变更应遵循预先定义的流转路径；不允许跳过必要审核，也不允许普通编辑把已确认单据改回任意状态。
14. 关键数据更正应采用更正、冲销、退货、反结算或重新核算等有痕方式，原始记录、变更原因和影响范围必须保留。
15. 业务发生日期、录入日期和审核日期应分别显示；补录历史业务时必须填写实际发生时间和补录原因。
16. 多个用户同时编辑同一条记录时，系统应检测记录版本；后提交者应收到冲突提示，并能查看最新内容后决定重新编辑、覆盖或放弃，不得静默丢弃任一方的修改。
17. 库存扣减、投苗数量变更、转塘、出塘、付款和收款等涉及数量或金额变化的操作，应以提交时的最新数据进行一次性校验和确认，发现余额不足或状态已变化时应阻止提交，避免重复扣减或超额处理。

### 20.1 统一交互反馈规范

系统所有页面应遵循以下统一使用规则，保证用户能够判断操作结果和下一步动作：

1. 所有新增、修改、删除、审核、出入库和导入操作完成后，应明确显示成功、失败、待审核、退回、取消或处理中结果，并告诉用户是否已经进入正式台账。
2. 删除、作废、取消、报废、冲销和状态切换前，应显示对象、影响范围和后续不可逆影响；用户确认后才能继续。
3. 列表没有数据时，应说明当前筛选条件下没有结果，并提供清除筛选、新建或导入的下一步入口。
4. 网络异常、提交失败或同步冲突时，应保留用户已填写的内容，说明是否已经写入，并提供重试、查看详情或放弃操作的选择。
5. 必填项、数量、金额、日期、状态和关联对象不符合业务规则时，应在提交前说明问题所在；提交后仍需再次确认业务结果。
6. 导入、导出、批量审核、批量出库和批量核算等耗时操作应显示进度或处理状态，处理期间不能重复产生同一批业务。
7. 列表应支持分页、检索、筛选和排序，并显示当前结果范围和总数量；筛选条件切换后应明确提示统计口径已改变。

## 二十一、原网站功能、优化版功能与新增功能总结

### 21.1 原网站已经具备或已经展示的功能

原网站已经形成较完整的业务菜单和页面框架，主要包括登录、数据看板、塘口档案、多塘分组、喂养计划、喂养记录、喂养派工闭环、日常非投喂作业、物料档案、入库、出库或领用、退库、库存盘点、库存预警、采购与应付、销售与应收、养殖成本核算、模板导入导出、用户账号、角色权限、操作日志和基础参数。

原网站的主要优点是业务范围广、岗位划分清楚、页面标题和菜单层级稳定、各类台账基本齐全，并且在看板中同时展示养殖、库存、成本和异常信息。

## 二十二、功能验收清单

层层审核时，可按以下顺序逐项确认：

### 22.1 登录与权限

1. 不同角色可以登录并进入不同的工作区。
2. 停用账号不能继续使用系统。
3. 角色只能看到授权功能和授权数据。
4. 采购、仓储、养殖、销售和财务之间的提交、审核、确认权限能够按岗位区分。
5. 权限调整、登录和退出都有记录。

### 22.2 塘口与分组

1. 可以建立完整塘口档案，并保存投苗、规格、存塘量和设备信息。
2. 可以切换塘口状态并查看状态变更历史。
3. 可以按照区域、品种、批次和负责人建立分组。
4. 可以建立投苗批次，登记抽样、损耗、转塘、分塘、合塘和出塘，并保持批次历史连续。
5. 清塘或关闭批次前，系统能够检查剩余存量和未完成业务。
6. 单塘、批次、分组和全场数据互相对应，不能出现统计口径不一致。

### 22.3 喂养与作业

1. 可以制定投喂计划并生成任务。
2. 作业员可以提交投喂记录、现场情况和照片。
3. 管理员可以审核、退回、作废和处理异常记录。
4. 派工任务能够看到计划量、实际量、差异、人员和完成状态。
5. 巡塘、换水、用药、增氧和设备维护记录可以查询并关联塘口。
6. 现场记录在网络不稳定时不会丢失，用户能够区分暂存、待同步和已确认状态。

### 22.4 物料与仓储

1. 可以建立物料档案并维护安全库存和保质期。
2. 入库、出库、退库和盘点能够正确更新台账。
3. 出库数量超过可用库存时不能提交。
4. 低库存、临期、过期和盘点差异能够产生提醒。
5. 任意库存变化都能追溯到单据、人员、时间和关联塘口。
6. 调拨、报损、报废和领用申请能够形成独立流程，并正确更新可用、在途和隔离库存。

### 22.5 采购、销售与成本

1. 采购记录能够关联入库并形成应付账款。
2. 销售记录能够关联塘口和品种并形成应收账款。
3. 付款和收款能够分次登记并自动显示未结余额。
4. 出塘事实与销售交易能够区分，部分交付、退货、冲销和坏账不会造成重复收入。
5. 九类成本能够按塘口、批次、分组和周期查看，并能打开费用来源。
6. 成本、收入和预计利润可以追溯到具体业务明细。

### 22.6 数据交换与报表

1. 用户可以下载正确的数据模板。
2. 导入前可以预览和查看错误行。
3. 文件存在错误时整批不写入，并能说明原因。
4. 各业务页面可以按筛选条件导出明细和汇总。
5. 导入批次、重复数据、撤销导入和后续业务引用关系能够被查询。
6. 导出结果包含统计范围和生成信息。

### 22.7 看板与消息

1. 看板能显示塘口、喂养、库存、采购、销售和成本关键指标。
2. 看板可以切换统计周期和筛选范围。
3. 指标能够进入对应明细。
4. 预警和待办有明确处理入口。
5. 已处理提醒不再重复显示为未处理事项。

### 22.8 Web、移动 App 与微信小程序

1. 同一账号在电脑浏览器和手机浏览器中能够按授权访问相同业务数据。
2. 手机浏览器能够完成登录、查看任务、快速录入投喂、登记非投喂作业、上传照片和查看消息。
3. 手机浏览器在弱网情况下能够保留未提交内容，并明确显示暂存、待同步和已确认状态。
4. 同一条记录在不同浏览器中不会因并发修改而静默覆盖，发生冲突时能够提示并处理。
5. 移动 App 与微信小程序使用当前后端 API、移动会话令牌和 CSRF/Cookie 连续性，不改变 Web 端业务规则和数据口径。
6. 移动 App 能够覆盖现场养殖、仓储、采购、销售、成本和数据交换主要流程，并在离线时保存待同步请求。
7. 微信小程序能够覆盖工作台、投喂、日常作业、物料领退、塘口、消息和个人作业历史。
